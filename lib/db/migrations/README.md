# Migrations

Generated by `drizzle-kit generate`, applied by `npm run migrate -w @workspace/db`.

## Why not `drizzle-kit push`

`push` diffs the live database against the schema and applies whatever it
decides is needed. There is no review step, no ordering guarantee, and no way
back — it will happily drop a column it thinks is gone. These files are
reviewable in a pull request, run in a fixed order, and are recorded in
drizzle's journal so re-running is a no-op. `push` remains available for
throwaway local databases only.

## `0000` is a baseline

The first migration creates `users`, `sessions` and `documents` together. It
assumes an **empty** database.

If you have a development database from before authentication existed, it
already has a `documents` table and applying `0000` will fail with
`relation "documents" already exists`. That data predates per-user ownership
and has no owner to assign, so the intended path is to recreate the database:

```sh
dropdb paper_formatter && createdb paper_formatter
npm run migrate -w @workspace/db
```

If you need to keep existing rows instead, add a user, then hand-write a
migration that adds `owner_id` as nullable, backfills it to that user's id, and
only then sets `NOT NULL` and the foreign key.

## Adding a migration

1. Edit the schema under `lib/db/src/schema/`.
2. `npm run generate -w @workspace/db`
3. Read the generated SQL. Drizzle cannot tell a rename from a
   drop-and-add — check for destructive statements before committing.
4. Commit the `.sql` file and the `meta/` snapshot together.

CI fails if the schema changes without a matching migration.
